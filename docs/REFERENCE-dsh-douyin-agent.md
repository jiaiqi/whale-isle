## 1. 结论摘要

**"验证边界 / 收据纪律"的生态范本**，也是把 `dsh-video-storyboard`（MIT）拼图源码复用进抖音场景的实例。核心价值不在抖音自动化本身（我们已否决浏览器方案），而在它把"AI 说了/做了"与"平台真实发生"之间的差距用**收据 + 回读核对 + 版本化验证记录**管理起来的工程方法——与我们 AGENTS.md 的回执铁律、docs/VERIFY.md 纪律完全互补。

## 2. 采用什么

- **收据基线**（`receipt-baseline.mjs`）：发送结果不确定时**保留收据并尝试回读核对；无法确认时不自动重发**；身份不符或发送结果不明时保留记录并核对——映射到我们所有"外发动作"（游戏操作、公屏回复、切片发布）的回执语义。
- **版本化验证记录**（`docs/verification/local-1.4.7-*.md`）：每次验证写明"本次验证范围 / 已验收项 / 待验项"，历史结果保留各自版本——`docs/VERIFY.md` 的记录格式直接参照。
- **测试纪律原文**："测试使用临时目录、合成模型或临时浏览器，**不应把测试通过写成真实平台联调通过**"——与我们 `[SIMULATION]` vs `[REAL-DEVICE]` 分栏同源。
- **每日额度账本**（`usage-ledger.mjs`）：观看分钟数 + 模型请求数双额度、暂停/重启/改设置不清空当天用量——饭碗扣费流水与"Token 消耗落盘 SQLite"的参照。
- **稳定身份识别**：收件人按平台稳定身份绑定，**"不用同名或头像猜测收件人"**——常客账本 uid 的去重原则。
- **无效决策防线**：无效或截断的观看决策不执行、重新观察后再判断，连续 3 次无效停止本次，每次调用仍计入预算——P0 队列防死循环参照。
- **分镜拼图**：多张 JPEG 采样拼成一张带格编号图（总像素预算 480000），复用 SAOS-3624/dsh-video-storyboard 的 MIT 源码；`douyin_video_zoom` 只保留**最近一分钟**采样、缓存有容量上限、退出或到期清理——**45 秒环形缓存**的实现思路同源。
- **许可名单（permission-based）**：好友互动须本人逐个许可会话，总开关默认不自行添加许可对象——直播互动边界（谁的话值得回）的保守设计。

## 3. 不采用什么（为什么）

- **浏览器自动化链路本身**（专用 Edge + Playwright 抓抖音页面）：SPEC 冻结决策是"弹幕走 dyhub 直连主线，不采用浏览器方案"；浏览器自动化对抖音 DOM 改版与风控脆弱，仅作思想参考。
- 抖音私信/好友互动/自主分享/公开评论等功能面：超出我们第一阶段范围（我们是直播中控，不是私信 bot）。
- QQ 共享记忆、表情选择等跨平台功能：不引入。

## 4. 验证路径、预算边界与回退方案

- 验证路径：不直接运行其代码；其"自检与用量 → 一键自检"的分项诊断思想可在我们 `tools/mock-harness` 的音频回环校验器中实现。
- 回退：若 dyhub 直连主线受阻，本仓库证明"浏览器只读抓弹幕 + 扩展回写"是可行兜底路线（`Dsh_douyin` 方式 A/B），但引入前须先过许可证与合规工单。
