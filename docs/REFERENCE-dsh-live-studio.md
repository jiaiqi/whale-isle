## 1. 结论摘要

**Live2D 舞台与直播账本的机制参照**：B 站弹幕 → 合并同观众问题 → TTS 回复 → agent 显式控制 Live2D 表情/动作（带播放回执）→ 浏览器源推流 → SQLite 账本。作者在 README 中自陈"**尚未完成全新 DSH 启动和真实直播验收**"——引用其机制结论时须注意成熟度，机制设计本身（目录/回执/过期）质量很高。

## 2. 采用什么

- **同观众问题合并**："接收 B 站直播弹幕、**合并同一观众的问题**、生成语音"——T-M4-01 合并逻辑的独立佐证。
- **Live2D 三工具设计**（预留 `Live2DRenderer` 接口时直接参照）：
  - `live2d_catalog`：列出当前模型**真实存在**的表情与动作（不虚构动作名）；
  - `live2d_perform`：按名执行；
  - `live2d_status`：**播放回执**；动作排队 30 秒未消费则过期。
  - 语义位：`keep` 保持表情 / `neutral` 恢复 / `none` 不新启动作 / `stop` 停止动作。
- **不自动映射情绪**："没有按台词关键词自动切换情绪的规则"——表情由模型显式选择，不做关键词正则硬映射（与我们的雷区正则区分：雷区是拦截，不是表演）。
- **渲染安全**：HTTP 只公开 model3.json 引用的素材，不公开目录其他文件；写接口保留回环地址、同源与令牌校验——obs-layer/pet-stage 本地 HTTP 服务的安全基线。
- **进程与频道锁**：相同 home 与直播间有进程锁，游戏控制还有频道锁——防止双实例双音轨。
- **回执口径（原文）**："任务已启动、动作已排队或凭据存在，都**不等于**最终成功"——AGENTS 回执铁律的又一表述。
- **账本诚实口径（原文）**："账本显示 API 用量估算和礼物标价，**不等于**平台结算到账"——Token 流水/礼物金额展示的免责口径。
- **合规边界**：不自动点击开播；Live2D 模型与 Cubism Core **不随包分发**、需自行取得许可——我们若做 Live2D 扩展须同样处理。
- **复用留痕**：复用鲸语（jingyu-live2d-agent）MIT 组件并在 NOTICE.md 保留上游来源——NOTICE 实践范例。

## 3. 不采用什么（为什么）

- **Edge TTS**：我们主线 GPT-SoVITS 本地优先（M2），不引入第二套 Python TTS。
- **blivedm** Python 弹幕依赖：B 站收流在归一层（`live-stream-hub`）处理，是否引入 blivedm 在 T-M4-01 复评时再定（其上游协议实现质量需单独评估）。
- DSH 插件宿主形态与 `?view=stream` 双页结构细节。

## 4. 验证路径、预算边界与回退方案

- 验证路径：其"单元测试覆盖配置拒绝、停用行为、聊天和媒体逻辑"清单可作 T-M1/T-M4 单测选题清单。
