## 1. 结论摘要

**仅吸收思想**。功能上是大肥鱼抖音直播间（OBS 1920×1080 场景：小说逐章朗读直播 + 章间语音互动不剧透 + 作品档案讨论 + 选题投票）+ 健身房直播间（弹幕排课、5301 动作库）。无许可证 + 内嵌 GPL 组件，代码一律不可复制；但其 README 是同生态中**最完整的"全自动直播工程实践记录"**，大量机制恰好验证了我们 SPEC 的设计方向。

## 2. 采用什么（思想层面）

- **TTS 分段预取**：1400–1600 字台词切 70–80 字小段，边播边合成下一段（预取一段），**首句 2–3 秒出声**、中间不空场——M2 长台词流式合成的直接参照。
- **`speakToken` 防叠音**：新一段开口前立刻掐掉上一段（speakToken 作废排队），**"不会两条音轨叠着说"**——我们 `AudioPlaybackLease`（单端语音锁）的朴素先行版，验证了语音锁的必要性。
- **TTS 四级降级链**：MiniMax Speech 2.8 HD（云端默认）→ edge-tts（免费在线）→ 本地 Kokoro ONNX（离线好听）→ 系统 SAPI（断网兜底）——与 `model-gateway` "本地优先 + 云端降级"同构；且合成结果按"模型+音色+情绪+语速+全文"哈希**本地缓存**（同文秒回）。
- **AI 503 三层兜底**：退避重试 ×3（1.2s→2.4s→4.8s，respect `retry-after`）→ 换 `fallbackModel` → 换备用接口（baseUrl+Key+model）；**长段失败不拿大纲糊弄过去**（等待重试，两次后才用兜底稿，下一段照常）——粘性路由故障转移的行为规格参照。
- **假接口自测**：`tools/fake-503.mjs` 起一个假 LLM 接口注入 503，验证重试与切换——`mock-harness` 故障注入剧本的现成思路。
- **点歌台真播放**：本地曲库/外链/自建 API 三源解析，`auto` 先本地后外链；Range 试拉 1KB 校验 content-type，**过不了就不算有源，不假装在放歌**；队列 max 3 拒绝时明确回话不静默丢弃；播完回调链自动下一首。
- **选题投票**：观众发"选题 XXX"进明天的候选票池——弹幕议会（20s 投票）的简化先例。
- **时段调度**：`broadcast.schedule` 按本地时钟切直播场景（健身/故事），切换经 SSE 通知且**暂停朗读防双音轨**——节目状态机 `GAMING_MAIN ↔ SINGING_CONCERT` 切换时的互斥参照。
- **计费记账**：usage 分"缓存命中输入/未命中输入/输出"按**官方现价 × 峰谷时段**计价，余额 60 秒缓存；"白饭余额 = riceBase + 今日收 × 0.1"的玩法公式——饭碗经济数值化参照。
- **诚实口径**："只有真收到的礼物才会被感谢"；"没有音源时**不会**假装正在放歌"。
- **RVC 训练门槛数据**：32k ≥8GB 显存 / 40k ≥12GB（T-M2-03 RVC 环境预算参考；其 6GB 显卡未跑成的教训直接可用）。
