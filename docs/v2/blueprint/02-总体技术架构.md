# 02 --- 总体技术架构

## 1. 架构原则

-   采用 **Modular Monolith + 独立 Worker**
    起步，不一开始拆成大量微服务。
-   Electron Desktop Host 作为本地交互入口；核心领域逻辑放在可测试
    packages 中。
-   所有外部能力通过 Adapter/Provider 接入。
-   跨模块状态变化通过明确的 Domain Event 或命令接口表达。
-   Character Identity 与 Agent Runtime、模型、设备、外观、声音解耦。
-   本地运行与云端协作通过版本化协议连接。
-   生产运行平面与研发平面严格隔离。

## 2. 三个平面

### Product Runtime Plane

桌宠、Agent、游戏、浏览器/电脑操作、声音和表演、直播和社交。

### Platform Services Plane

Model Gateway、Provider Registry、Plugin Runtime、MCP Gateway、Skills
Registry、Account Vault、Device Registry、Asset Registry、Event
Store、Memory Store、Observability、Quota Center。

### Development Plane

独立 Whale Isle Evolution Engine
负责诊断、工单、源码修改、测试、审查、PR、构建、发布和回滚。

研发平面不应与生产角色共享高权限凭证或直接操作生产数据库。

## 5. 关键模块边界

-   **Character
    Core**：身份、人格、偏好、关系引用和状态定义，不直接调用模型或控制设备。
-   **Agent
    Runtime**：思考、规划、工具调用、任务状态和会话。第一阶段只有一个主
    Runtime。
-   **Embodiment
    Runtime**：把角色状态映射为桌宠、游戏角色、Live2D、VRM、舞台等表现。
-   **Model Gateway**：LLM Provider、模型配置、路由、成本和调用日志。
-   **Media Generation Gateway**：图片、3D、音频、视频生成
    Provider；不混入 LLM Gateway。
-   **Asset
    Registry**：素材版本、格式、哈希、来源、许可、用途和发布状态。
-   **Digital Life
    Runtime**：生活计划、内容探索、社区任务和自主行为；不能绕过 Policy
    Engine。
-   **Evolution Engine**：独立研发控制系统。

## 6. 进程和部署

第一阶段可采用 Electron 主进程、React Renderer、本地核心服务、语音
Worker、媒体生成 Worker、游戏 Mod 和可选浏览器 Worker。

后续再增加多设备 Node、可选云端同步、视频理解 Worker 和独立 Evolution
Engine。

不要为了微服务化而过早引入 Kubernetes
或复杂服务网格。先确保单机体验和协议边界稳定。

## 7. 事件驱动

``` ts
interface DomainEvent<T> {
  eventId: string;
  eventType: string;
  schemaVersion: number;
  occurredAt: string;
  source: {
    deviceId?: string;
    agentRuntimeId?: string;
    characterId?: string;
    module: string;
  };
  correlationId?: string;
  causationId?: string;
  payload: T;
}
```

事件示例：`character.mood.changed`、`voice.speech.started`、`game.action.completed`、`live.chat.received`、`social.content.discovered`、`memory.episode.created`、`asset.version.published`。

需要即时返回和强一致性的操作使用
Command/Response；事件用于通知已发生的事实。

## 8. 状态一致性

角色身份是权威数据源；各种 Embodiment
是角色状态投影。游戏状态与桌面状态通过明确映射同步。多设备事件使用唯一
ID、时间戳和幂等键。网络断开时允许本地缓存事件，恢复后按领域规则合并，不能简单地全部使用最后写入覆盖。

## 9. 多设备模型

每台电脑是一个 Device Node，拥有本地桌宠渲染、游戏实例、Browser
Profile、Computer Use Lease、素材缓存和能力声明。

一个 Agent Runtime 可在指定设备运行；一个角色可在多种 Embodiment
中呈现。第一阶段只保证一个主 Runtime，不做复杂多主并发。

## 10. 工程技术原则

-   TypeScript/Zod 用于共享协议和运行时校验；
-   IPC/网络 API 必须版本化；
-   第三方插件尽可能进程隔离；
-   文件系统和账号凭证通过专门服务访问；
-   长任务使用 Job ID、进度和取消机制；
-   所有异步任务必须有超时、重试、幂等和取消策略；
-   所有用户可见自动化都有状态和日志。

## V2.1 增补：Game Agent 决策子系统

Game Runtime 需要进一步拆分为 Game State Adapter、World Model、Goal Manager、Decision Planner、Game Knowledge Base、Experience Memory、Conversation Co-op、Command Router、Control Arbiter、Action Executor 和 Result Verifier。

LLM 负责理解、目标生成和策略判断；结构化 Game Adapter 提供真实状态与动作接口；Control Arbiter 负责用户输入和 AI 自主行动的优先级。不要把游戏策略硬编码在 Adapter 中。详见 `17-自主游戏智能与人机共玩系统.md`。
