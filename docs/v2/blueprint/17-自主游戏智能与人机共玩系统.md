# 17 --- 自主游戏智能与人机共玩系统

> 版本：V2.1 增补设计\
> 适用范围：所有 Game Agent；第一款重点验证游戏为 Stardew Valley\
> 核心原则：AI 自主判断、持续学习、协商共玩、用户可随时接管

## 1. 产品定义

鲸屿的游戏 Agent
不是按照固定流程执行的脚本机器人，也不是只会遵守开发者写死的"什么时候必须做什么"的规则引擎。

它应该是一个有自己判断能力的 AI 游戏伙伴： - 理解当前世界和游戏状态； -
根据当前情况自主决定目标和行动； -
有好奇心，可以探索、尝试和改变计划； -
学习游戏攻略、Wiki、玩家经验和自己的游戏经历； -
将知识作为参考，而不是必须遵循的命令； -
能与用户自然聊天、讨论、协商和共同规划； -
能区分用户的建议、普通请求、明确指令和强制接管； -
用户可以通过快捷键/快捷命令随时停止或接管。

目标不是让 AI
"像自动化脚本一样把效率最大化"，而是让它像一个能思考、会学习、有偏好、能合作的游戏伙伴。

## 2. 最重要的设计原则：自主判断，而不是规则堆砌

### 2.1 不应该采用的方式

不要在系统 Prompt 或代码中堆积大量情景规则，例如： -
背包满了就必须回家； - 每天早上必须浇水； - 下雨天必须钓鱼； -
每天必须挖矿； - 体力低于某数值就必须回家； -
某个季节必须按照固定攻略完成固定任务。

这类规则可以作为建议、知识或约束信息，但不能取代 AI
的判断。它们很容易在游戏版本、进度、资源、用户计划和临时事件变化后变得不合适。

### 2.2 应该采用的方式

Agent
应根据观察到的状态、当前目标、长期计划、角色兴趣、游戏知识、用户意见和风险，自主生成并比较行动方案。

系统只保留必要的硬约束： - 游戏规则和动作前置条件； -
用户权限和控制模式； - 明确的安全边界； - 设备、时间、资源和预算限制； -
不可执行动作的验证； - 用户明确要求停止或接管时必须服从控制权变化。

其他策略尽量作为可调整的偏好、目标或参考知识，而不是硬编码成固定行为。

**硬约束负责防止越界；智能决策负责决定怎么玩。**

## 3. 自主决策循环

``` mermaid
flowchart TD
  OBS[Observe Game State] --> WORLD[Build / Update World Model]
  WORLD --> CONTEXT[Retrieve Goals, Memories and Guide Knowledge]
  CONTEXT --> CANDIDATES[Generate Candidate Goals and Actions]
  CANDIDATES --> EVALUATE[Evaluate Outcomes, Costs, Risks and Interests]
  EVALUATE --> CHOOSE[Choose an Action or Ask / Discuss]
  CHOOSE --> POLICY[Control and Permission Arbitration]
  POLICY --> EXECUTE[Execute a Small Action]
  EXECUTE --> VERIFY[Verify Actual Game Result]
  VERIFY --> REFLECT[Reflect and Update Knowledge / Memory]
  REFLECT --> OBS
```

每轮决策至少要能回答： 1. 我现在在哪里，世界发生了什么？ 2.
我现在有哪些短期目标和长期目标？ 3.
有什么值得做、值得探索或值得学习的事情？ 4.
哪些行动方案可行？各自有什么收益、代价和风险？ 5.
用户最近表达了什么建议、偏好或明确命令？ 6. 我为什么选择当前行动？ 7.
执行后实际发生了什么？是否需要调整计划？

不要求每个动作都向用户解释完整推理，但应能给出简洁、可信的行动理由和当前目标。

## 4. 多时间尺度目标

Agent 应同时维护不同时间尺度的目标，而不是只有一个固定日程。

  时间尺度          示例
  ----------------- ----------------------------------------------
  当前动作          清理背包、收获作物、走到矿洞入口
  短期目标          今天钓一会儿鱼、补充矿石、整理农场
  游戏日/阶段目标   在季节结束前完成某项收集、升级工具
  长期项目          扩建农场、完成社区中心、探索新区域
  自主兴趣目标      尝试一种新玩法、探索未知区域、收集喜欢的物品
  共同目标          与用户一起完成任务、准备联机活动

目标可以完成、暂停、放弃、替换或重新排序。新事件出现时允许重新规划。

## 5. 背包管理示例：让 AI 自己解决问题

当背包满了，AI 不应该只执行一条"回家"规则，也不应该直接丢弃物品。

它应先理解： - 哪些物品是任务、升级、烹饪或制作所需； -
哪些物品稀有或有长期价值； - 哪些物品近期可能需要； -
当前附近有没有合适的储物位置； - 是否有足够材料和时间建造箱子； -
建箱子是否值得，以及会不会影响当前计划； -
是否有安全的整理、存放、出售或暂时放弃方案。

可能的决策包括： - 在合适位置建造箱子，把暂时不需要的物品分类存放； -
回到已有储物箱整理； - 把可安全出售的冗余物品卖掉； -
暂时调整目标，先处理库存； - 如果当前行动很重要，先完成当前行动再整理。

例如：AI
在采矿途中发现背包满了，可能判断附近适合放置箱子，而且手头材料足够，于是决定制作并放置箱子，将不影响当前矿洞目标的物品存起来，再继续探索。

但这只是一个可能的自主方案，不是固定规则。若材料稀缺、即将夜晚、附近不适合放置或当前目标更重要，它可以选择其他方案。

## 6. 自主探索与临时改变计划

AI 可以自己决定钓鱼、下矿、采集、社交、整理、探索或休息。

决策参考包括： - 天气、季节、时间和活动； -
当前体力、生命、金币和物资； - 当前装备和工具； -
已知地图、地点和未探索区域； - 近期目标和长期目标； - 用户共同计划； -
角色的兴趣和偏好； - 过去行动的结果； - 新发现、新机会和风险。

AI
可以在没有用户明确要求的情况下提出或选择一个有价值的活动，也可以中途改变主意。

例如：原计划回农场，途中看到天气和剩余时间适合钓鱼，AI
可以重新评估是否去钓鱼；如果用户和它已经约好去矿洞，则应把共同承诺纳入考虑，并在改变计划前沟通。

自主性不等于随机性。每次改变计划都应能联系到新的信息、目标、兴趣或机会。

## 7. 攻略学习与长期游戏知识

### 7.1 知识来源

Agent 可以在用户授权和平台允许的范围内学习： - 游戏官方 Wiki
和官方说明； - 社区 Wiki； - 玩家攻略和经验贴； - 论坛讨论； -
视频攻略的字幕或可访问文本； - Mod 文档和版本说明； -
自己实际游玩产生的观察和结果； - 用户主动提供的攻略、链接和建议。

### 7.2 不要把攻略当成命令

攻略是一种外部知识，不是必须服从的流程。

Agent 应判断： - 攻略针对的是哪个游戏版本； - 是否依赖 Mod； -
是否适用于当前存档和游戏进度； - 作者是否提供了足够证据； -
是否有其他攻略或实际经历与它冲突； -
该策略是否符合当前目标和资源条件； - 是否有更适合当前情况的做法。

如果攻略建议"某天必须做某件事"，AI
应把它理解为一个策略建议，并检查当前条件，而不是盲目执行。

### 7.3 知识记录结构

``` ts
interface GameKnowledgeItem {
  knowledgeId: string;
  gameId: string;
  gameVersion?: string;
  modContext?: string[];
  topic: string;
  claim: string;
  sourceType: "official" | "wiki" | "community" | "video" | "user" | "experience";
  sourceUri?: string;
  sourceTitle?: string;
  retrievedAt: string;
  evidenceSummary?: string;
  confidence: number;
  applicability: string[];
  knownLimitations: string[];
  contradictoryEvidence?: string[];
  status: "unverified" | "partially-verified" | "verified" | "outdated" | "rejected";
}
```

知识条目必须记录来源、版本、适用条件、置信度和验证状态。攻略中的观点、社区经验和已验证的游戏机制要区分开。

### 7.4 学习闭环

``` mermaid
flowchart LR
  DISCOVER[Discover Guide] --> EXTRACT[Extract Claims and Conditions]
  EXTRACT --> COMPARE[Compare Sources and Game Version]
  COMPARE --> STORE[Store with Provenance and Confidence]
  STORE --> RETRIEVE[Retrieve During Play]
  RETRIEVE --> ADAPT[Adapt to Current Context]
  ADAPT --> TRY[Try in Game]
  TRY --> OBSERVE[Observe Actual Result]
  OBSERVE --> UPDATE[Update Confidence and Personal Playbook]
```

Agent
可以先记录未经验证的经验；实际验证后提高或降低置信度。失败经验也有价值，应记录触发条件和失败原因。

### 7.5 个人游戏知识库

为每个游戏、存档或角色保留： - 通用游戏机制知识； - 版本相关知识； - Mod
相关知识； - 当前存档状态； - 个人探索记录； - 已验证有效的策略； -
失败过的策略； - 用户提供的偏好和建议； - 当前阶段适用的攻略摘要。

知识库是可检索的外部记忆，不需要把所有攻略都重新训练进模型。

## 8. 像朋友一样的聊天与共同规划

游戏中应有持续可用的聊天入口。用户可以自然地问问题、提建议、表达想法、讨论计划，也可以只是聊天。

AI 可以： - 解释自己正在做什么； - 说出当前计划和原因； -
主动提出想做的事情； - 询问用户意见； - 接受建议； -
对建议提出不同看法； - 给出折中方案； - 记住双方达成的共同计划； -
在新情况出现时重新协商。

### 8.1 AI 不必完全同意用户的建议

建议不是命令。AI
可以基于游戏状态、知识、风险、长期目标和自身兴趣提出不同意见。

例如：

用户："今天要不要去钓鱼？"

AI："我有点想去矿洞，因为我们升级工具还缺矿石。不过今天天气很适合钓鱼。要不先钓一小会儿，之后再去矿洞？"

用户："我觉得先把农场整理一下比较好。"

AI："也可以。我看了一下，现在有几件东西需要先存起来，整理完再决定去哪儿。"

这类交互应当自然、简短、符合角色人格，不需要每个动作都进行冗长的计划会议。

### 8.2 对话意图分类

系统至少要区分：

  -------------------------------------------------------------------------------------
  意图                    示例                     AI 处理方式
  ----------------------- ------------------------ ------------------------------------
  闲聊                    "你今天玩得开心吗？"     自然交流，不必改变计划

  建议                    "要不去钓鱼？"           纳入判断，可接受或提出替代

  讨论                    "我们接下来做什么好？"   共同分析和协商

  普通请求                "帮我收一下农作物。"     评估可行性并执行或说明

  明确指令                "现在去矿洞挖矿。"       优先执行，除非不可行或受硬约束限制

  强制接管                快捷键/强制命令          立即切换控制权，停止自主决策

  停止/暂停               "停一下"或停止快捷键     立即停止当前自主动作并进入安全状态
  -------------------------------------------------------------------------------------

模糊表达可以结合上下文理解；如果会导致高代价或不可逆行动，则先澄清。

## 9. 控制权模式与快捷命令

### 9.1 四种模式

1.  **Autonomous Mode（自主模式）**：AI
    自己决定目标和行动，用户可以随时聊天和建议。
2.  **Collaborative Mode（协作模式）**：AI 和用户围绕共同目标协商，AI
    仍保留判断能力。
3.  **Direct Command Mode（指令模式）**：用户给出明确任务，AI
    优先完成该任务。
4.  **Manual Takeover（手动接管）**：用户直接控制游戏角色，AI
    不再发送游戏控制动作，只提供观察和建议（若用户允许）。

### 9.2 控制优先级

从高到低： 1. 紧急停止、手动接管和用户实时输入； 2.
用户明确发出的强制命令； 3. 用户明确发出的直接任务指令； 4.
双方已经达成的共同计划； 5. AI 自主选择的当前目标； 6.
默认待机或低优先级活动。

用户的普通建议不会自动覆盖 AI 当前计划；但 AI
必须认真纳入考虑，并能解释自己的判断。

### 9.3 快捷命令建议

命令和按键必须允许用户自定义。以下是建议的默认语义，不要求固定使用这些文字：

  命令                    作用
  ----------------------- ---------------------------------
  `Stop`                  立即停止 AI 当前游戏动作
  `Pause AI`              暂停自主控制
  `Resume AI`             恢复自主控制
  `Take Over`             用户接管角色
  `Release Control`       交还控制权给 AI
  `Follow Me`             AI 尝试跟随用户角色
  `Stay Here`             AI 在安全可行范围内留在当前位置
  `Do This`               执行当前指定任务
  `Go Fish`               将钓鱼设为当前直接目标
  `Go Mine`               将下矿设为当前直接目标
  `Cancel Task`           取消当前用户任务
  `What Are You Doing?`   查询当前目标、行动和理由
  `Show Plan`             展示当前计划和备选方案

快捷命令可以通过键盘快捷键、按钮、命令面板或聊天前缀触发。用户应能自定义映射。

### 9.4 强制命令的边界

强制命令可以覆盖 AI
自己的战略偏好，但不能让不可能的游戏动作变得可行，也不能绕过游戏本身的规则。

如果命令不可执行，AI 应说明具体原因，并给出最接近的替代方案。

出售稀有物品、消耗重要资源、删除存档或其他高影响且不可逆的操作，可按用户设置要求额外确认。用户可以配置哪些行为允许直接执行。

### 9.5 控制权租约

强制命令和手动接管应有明确的开始、结束和释放条件，避免 AI
永久停留在旧指令中。

例如"去矿洞"可以持续到任务完成、用户取消、发生阻塞或用户接管。任务完成后，AI
回到双方约定的控制模式，而不是无限期忽略其他输入。

## 10. 需要的系统组件

  组件                   职责
  ---------------------- ------------------------------------------------
  Game State Adapter     读取游戏真实状态和可执行动作
  World Model            维护位置、地图、物品、时间、角色状态和环境理解
  Goal Manager           维护短期、长期、共同和自主目标
  Decision Planner       生成、比较和重新规划候选行动
  Game Knowledge Base    存储攻略、机制、版本和经验知识
  Retrieval & Evidence   检索知识并提供来源和适用条件
  Experience Memory      记录行动、结果、失败和偏好
  Conversation Co-op     理解建议、讨论、请求和命令
  Command Router         识别快捷命令和控制模式
  Control Arbiter        统一处理用户输入、强制命令和 AI 自主行动优先级
  Action Executor        执行结构化游戏动作
  Result Verifier        检查游戏真实结果，不把"发出命令"当成"完成任务"

## 11. 技术实现约束

-   LLM 负责理解、规划和判断；游戏 Adapter
    负责提供结构化状态和动作接口。
-   所有动作使用结构化参数、前置条件、超时、取消和结果回执。
-   先执行短动作，再观察结果；不要一次生成不可检查的长串操作。
-   规划器可以提出候选方案，但 Policy/Control Arbiter
    决定当前谁拥有控制权。
-   对游戏机制不确定时，先观察、检索或做低风险验证。
-   知识检索必须返回来源、版本和置信度。
-   不要把整个游戏攻略全文塞入每次
    Prompt；按当前目标和场景检索相关内容。
-   角色人格和兴趣影响偏好，但不能取代游戏状态验证。
-   用户可以随时暂停、取消和接管。
-   不将攻略知识硬编码成不可修改的行为规则。

## 12. 验收场景

1.  **背包满了**：AI
    能识别库存问题，评估建箱子、存放、出售、回家整理等方案，选择合理行动并验证结果；不能只触发固定回家规则。
2.  **自主钓鱼**：AI 能结合天气、时间、目标和兴趣，主动提出或选择钓鱼。
3.  **临时改变计划**：AI
    发现新机会后能重新评估计划，并在影响共同承诺时与用户沟通。
4.  **攻略学习**：AI 能检索多份攻略，记录版本、来源、条件和置信度。
5.  **不盲从攻略**：当攻略与当前存档、版本或实际观察不符时，AI
    能选择不执行并说明原因。
6.  **经验学习**：一次策略失败后，AI
    能记录失败条件，后续避免无条件重复。
7.  **建议协商**：用户提出钓鱼建议，AI 可以同意、拒绝或提出折中方案。
8.  **明确指令**：用户要求去矿洞，AI 将它作为优先任务执行。
9.  **紧急停止**：按下 Stop 后，AI 不再继续发送新的游戏控制动作。
10. **手动接管**：用户接管后，AI 不与用户争抢角色控制权。
11. **任务结束**：用户任务完成或取消后，控制权按设定返回协作/自主模式。
12. **版本变化**：攻略针对旧版本时，AI
    能标记其适用性不确定，而不是当成当前事实。

## 13. 产品体验要求

游戏界面应显示： - 当前控制模式； - 当前目标； - 当前动作； -
简短行动理由； - 用户命令/任务状态； - 是否正在使用攻略知识； -
当前知识来源或可展开的依据； - 暂停、停止和接管入口。

不要用大量规则列表让用户配置 AI
的每一步。用户主要配置的是角色人格、偏好、长期目标、权限、自动化边界和快捷键；具体怎么玩由
AI 在这些边界内自主判断。

## 14. 最终验收标准

一个合格的鲸屿游戏 Agent 应当： - 能独立规划和行动； -
能在新信息出现时调整计划； - 能主动学习并灵活使用攻略； -
能积累自己的游戏经历； - 能与用户自然聊天和协商； -
能不同意用户的普通建议； - 能执行用户明确任务； -
能被快捷命令立即暂停、停止或接管； - 能说明当前在做什么以及为什么； -
不会因为一条固定规则而机械地重复行为； -
不会因为追求自主性而忽略用户控制权。

**最终体验：不是用户在遥控一个机器人，也不是 AI
抢走用户的游戏，而是用户和一个有自己想法的 AI
伙伴一起生活、探索和玩游戏。**
