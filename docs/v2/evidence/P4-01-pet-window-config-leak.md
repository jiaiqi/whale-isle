# P4-01：桌宠窗口配置累积修复

## 决策声明

采用「一次性伴生桌宠关闭后不再写回磁盘配置」的修复，替换原先「保留关闭坐标但对 `pet-` 前缀封顶 12 个」的做法；参考 dsh-pet 单实例生命周期思想与本仓「单角色小鲸」主线约束，自行实现。只清理临时召唤类窗口（`pet-` / `egg-` 前缀）的持久化记录，**不改动用户明确创建的常驻桌宠坐标**，也不改变任何召唤与排布逻辑。

验证：以真实磁盘上累积的 13 条 `pet-crosspet-claude-*` 孤儿记录为样本写回归；覆盖一次性伴生桌宠关闭后不再写回、常驻桌宠坐标仍保留、主桌宠保留。再跑完整门禁。

## 真实发现（用户截图「多层桌宠重叠」线索）

启动后用辅助功能列窗口，得到 3 个窗口：

```
鲸屿 · 桌宠 pet-crosspet-claude-9k54
鲸屿 · 桌宠
鲸屿 · 中控台
```

读取真实 `pet-window-prefs.json` 发现 **13 条**窗口记录，其中 12 条是 `pet-crosspet-claude-*`，且**多个坐标完全相同**（`966,694` 出现 4 次）。

根因链路：

1. `pet-control-host.ts:145` 生成一次性伴生桌宠 id：`pet-${character}-${时间戳}`。
2. `pet-window-manager.ts` 的 `save()` 对已关闭窗口的持久化记录**一律保留**，只对 `pet-` 前缀**封顶 12 个**（`egg-` 直接跳过）。
3. 于是每次「召唤伴生桌宠 → 关闭」都会在磁盘留下一条孤儿记录，持续累积。
4. 同一角色不并存校验（`findCharacterHolder`）虽按角色家族归一，但历史遗留仍使配置膨胀，并可能被按 id 遍历的逻辑误当成需恢复的桌宠。

补充确认：启动路径 `index.ts:1681` 只 `open('default')`，**不会**自动恢复这 12 条，因此启动重影另有成因；但配置无限累积本身是确凿缺陷，且与用户「好多层桌宠重叠」的观感高度相关。

## 实现

- `save()` 中跳过 `egg-` 与 `pet-` 前缀的历史记录，不再封顶保留。
- 常驻/自定义 id 的关闭坐标保留逻辑不变（`agent-2` 既有测试仍通过）。
- 磁盘历史残留已手工清理：13 条 → 1 条（仅 `default`）。

## 验证

- `pet-window-manager.spec.ts` **17/17 通过**（无覆盖率门槛运行），新增用例覆盖上述三项。
- 测试过程中两次失败均如实记录：首次未等防抖落盘；第二次误判常驻 id 保留时机（须先落盘再关闭），已按真实实现修正。
