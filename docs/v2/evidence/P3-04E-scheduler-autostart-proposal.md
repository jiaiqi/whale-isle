# `V2-P3-04E` 遗留：scheduler tick 自动发起社交会话 — 方案（待 owner 拍板，未实现）

> 状态：**仅方案，代码未动**。`V2-P3-04` 以 `IMPLEMENTED_UNVERIFIED` 封口时如实记录了「scheduler tick 自动发起会话的循环未接（当前手动/事件驱动）」。本文只回答四个问题：触发间隔怎么定、单次预算、急停在哪、owner 能看到什么。

## 0. 现状（已具备的底座）

- `SocialRuntime` 已有 `planSession → startSession → tick → complete/abort` 状态机，能力矩阵「授权 + 已实测」双条件门禁，`maxItems` / `maxDurationMs` 预算自动收官。
- `LifeRuntime` 已有暂停/急停语义；`P0` 急停会撤销所有控制租约。
- 宿主已有 `v2:social-*` IPC 与中控台生活页面板，会话状态可见。

缺的只是一层「什么时候该发起」的调度，以及发起后的可见性与刹车。

## 1. 触发间隔怎么定

建议三段式，全部可配置、默认保守：

- **基础节律**：每 90–150 分钟最多发起 1 次，实际间隔在区间内加 ±20% 抖动，避免整点机械感。
- **每日预算**：每天最多 2 次、累计 ≤30 分钟，跨日重置（按角色本地时区游戏日/自然日均可，建议自然日）。
- **冷却**：上一次会话以 `aborted` / 失败 / 预算耗尽收官后，至少冷却 60 分钟；连续 2 次失败当日不再发起，并在生活页明示原因。

调度只决定「何时可以开始」，不决定「看什么、怎么互动」——后者仍由 `LifeRuntime` + 模型判断，符合 ADR-002 的 AI-First 红线（不用固定策略代替判断）。

## 2. 单次动作预算

沿用现有契约字段，不新增语义：

- `maxItems` 建议 20（L1 只读浏览，看 20 条足够形成兴趣信号）。
- `maxDurationMs` 建议 10 分钟；到点无论看到第几条都自动收官，并如实记录 `stopReason`。
- 单会话内容理解最多 8 次模型调用（每 2–3 条抽一次），避免 token 失控；超额时停止理解、只记浏览事实。
- 平台能力未实测（`lastVerifiedAt=0`）一律不发起；L1 只读，不点赞、不评论、不发布。

## 3. 急停在哪

- **P0 急停**（现有按钮/快捷键）：立即 `abort` 当前会话 + 停 tick + 撤销控制租约，生活页显示「已急停，自主生活暂停」。
- **「暂停自主生活」开关**（现有 `LifeRuntime` 暂停）：tick 直接不触发，已有会话正常收官。
- **模型不可用**：不静默退化为规则浏览，按 ADR-002 安全暂停并提示（与当前 `paused` 口径一致）。
- **用户正在用电脑 / 正在直播 / 正在玩游戏**：tick 让路，不发起（避免抢焦点与资源）。

## 4. owner 能看到什么

中控台「生活」页建议四块，全部读真实状态、零假指标：

- **下次可发起时间**（含被谁拦住的原因：预算用完 / 冷却中 / 平台未授权 / 已暂停）。
- **当前会话**：平台、标题、已看条数 / 上限、剩余时长、当前状态。
- **今日用量**：次数、累计时长、最近一次停止原因。
- **最近 5 次记录**：发起时间、收官原因、产生的兴趣信号条数。

桌宠气泡只报两条：会话开始一句、收官一句（复用 `social.session.*` 已有投影），不逐条刷屏。

## 5. 风险与回退

- 默认**关闭**（`autostart=false`），owner 在设置里显式打开才生效；一键关即回退到现状（手动/事件驱动）。
- 所有发起都走现有能力矩阵门禁，不会因为 tick 而绕过授权或平台限制。
- 失败/异常一律自动冷却 + 如实报错，不重试轰炸。

## 6. 需要 owner 拍的四个点

1. 默认开关：关闭（建议）还是开启？
2. 每日次数与累计时长：2 次 / 30 分钟是否合适？
3. 夜间时段（如 00:00–08:00）是否完全禁止发起？
4. 连续失败后当日停发，还是允许隔 3 小时再试一次？
