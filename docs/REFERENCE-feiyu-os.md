## 1. 结论摘要

让"**会睡着的会话**"组成自推进团队的全部底座：信箱（五种消息）· 班次（心跳+定向唤醒+看护）· 工单制 · 记忆图谱 · 裁判（Eval）· observe→auto 切闸。对我们的价值不在"多 agent 编排"本身（其自述：没有中央编排器，假设席位会下线），而在**确定性准入纪律**（observe 先于 auto）、**唤醒分级**（P0/P1/P2 的原型）、**契约升级纪律**（夹具 + 双侧探针）。冻结决策已明确剔除其常驻唤醒与私有 SQLite 耦合。

## 2. 采用什么

- **observe 先于 auto（最重要的开关纪律）**：任何新能力先跑 observe 档只记录 `would_accept` 不真执行，跑几天与人工判断对账，对上了才切 auto（真实代价：切闸前 4/4 窗口对账抓出 100% 假阳性）——**我们"仿真沙盒先行 + VERIFY 分栏"的最强外部印证**；雷区反射、注意力队列等上线前均应走 observe→auto 两档。
- **唤醒分级**："轻的落笔记、中的开工单、值得开口的才来打扰人"——P0/P1/P2 注意力队列的语义原型；且"每条信息先过裁判（强度/预算/去重）"→ `DANMAKU_FAST_ROUTER` 槽位的职责定义。
- **事件唤醒**：星露谷换日、鱼竿卡住等游戏事件直接唤醒并开工单——游戏事件进注意力队列（而不只是轮询）的设计佐证。
- **信箱五消息**：`LOCK`（动共享资源前）/ `PROGRESS` / `DONE`（带路径与数字）/ `HANDOFF` / `ASK`+`ACK`（15 分钟无回执即升级）——跨模块长任务的消息回执协议参照（尤其 `game-bridge-mcp` 长动作与 `audio-ai-worker` 合成任务）。
- **契约升级纪律**：改契约的顺序固定——先改契约正文 → 加夹具（51 条 + 9 变异体）→ 两个实现各自改 → **双侧 probe 全绿才算契约成立**；"一段文字两身体通用"（同一 wait 契约跨游戏）——`shared-protocol` 跨语言导出器（T-M0-02）应配**夹具 + TS/Python 双侧探针**，超出我们原定门禁强度，值得吸收。
- **记忆图谱**：逐回合吸入 → LLM 抽取 → 向量化（per-chat 独立库）→ 每晚蒸馏成第二天开场；断档自愈（17 小时静默后回灌工具逐轮补回）——`persona-brain` 长期记忆与"睡前蒸馏"的设计参照。
- **看护兜底（奶妈进程）**：玩过头拉回睡觉、没体力塞饭、卡住修脚本、节日先查攻略——脚本做亚分钟级照护、会话只做判断——游戏托管安全网（`game-bridge-mcp` 的 `PAUSED_BY_PROGRAM`/预算边界的行为参照）。
- **隐私纪律**：唤醒通道只带一句固定话术，正文永远走信箱——弹幕/私信内容不进日志告警通道的同类思路。

## 3. 不采用什么（为什么）

- **常驻 20 分钟心跳 / 夜班航海队 / 六席团队**：那是 7×24 开发团队机制（船长每 20 分钟醒一次分活），不适配桌宠/直播场景的单实例节奏——SPEC 冻结剔除项，维持不变。
- **私有 SQLite 耦合**：其记忆图谱独立仓自带存储；我们统一主进程 `better-sqlite3` 单点事实源——维持不变。
- **平台仓 + 车道仓两层仓结构**：我们是单 monorepo（`dependency-cruiser` 锁边界已足够）。
- **QQ 线 / 服务器部署 / 眼睛视觉层**：超出范围；其 feiyuos-eye 的"三分区闸"仅在视觉预算设计时再回头看。

## 4. 验证路径、预算边界与回退方案

- 验证路径：不引入其运行时；其"案例"文档（夜班、observe 对账、记忆断档、静默失败三关校验）作为我们 VERIFY.md 反例清单的来源（尤其"文件改对了不等于进程里跑对了"）。
- 回退：若 observe→auto 双档在 UI 上太复杂，先落"模拟器全绿才允许接真实直播/游戏"的单档纪律（本仓 Gate 4 已覆盖一半）。
